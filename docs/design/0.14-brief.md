# deployctl 0.14 — brief: one console for all your projects

Hand-off for a fresh planning session. Short on purpose: plan from this, then read the code.

---

## Goal

On one laptop, a person sets up **once** (their GitHub login), then **adds any number of
projects** and **switches between them from the panel**. Adding a project is either **a new
first deployment** or **importing a teammate's export**. The docs let someone who has never
seen deployctl go from nothing to a live, auto-deploying project.

## 1. One setup per person — the `gh` login

- **What:** the person's GitHub login (`gh`) is the only setup they do, once, for all
  projects.
- **Registry access:**
  - **Default:** the `gh` login's token (after `gh auth refresh -s read:packages`), with the
    username from `gh api user`. Used for the tag picker, and for host pulls the laptop drives
    (first deploy, Emergency).
  - **Optional, stricter:** a `read:packages`-only token, created through a prefilled link
    (`github.com/settings/tokens/new?scopes=read:packages&description=deployctl-registry`) and
    stored once in `~/.deployctl/credentials.env` (0600). For people who don't want their
    broad `gh` token ever touching a server.
  - **Order of precedence:** process environment (CI's `GITHUB_TOKEN`) → project
    `config/local.env` (0.13, kept as a per-project override) → the global file → the `gh`
    login.
  - **Resolve at the point of use** (the engine's environment, the tag picker), in a new
    `cli/access.py`. Keep it out of the config layers, so the shared configuration stays
    identical on every machine.
- **CLI:** `deployctl access` shows gh login, `read:packages` scope, registry source, and this
  machine's public ssh key. It prints the exact command for anything missing.
- **Panel:** *Your access* uses it.
  - Registry access is **optional** for someone who only ships through GitHub (CI needs no
    personal credential).
  - SSH shows the public key plus the one command the project owner runs to add it.
- **Unchanged:** CI logs in with its own token; hosts are logged out after every pull (0.13).

## 2. Many projects, one panel — the switcher

- **One process per project**, as today; **no** single process that switches projects.
  - Keeps the safety property that a panel can only act on its own project.
  - Avoids refactoring `cli/paths.py`'s global state.
  - Keeps each project's running jobs where they are.
- **Registry of projects:** `~/.deployctl/projects.toml`: name, repository path and a
  **stable port** each. Nothing secret.
- **CLI:** `deployctl projects list | add PATH | remove NAME`. The panel runs these (panel =
  CLI).
- **`deployctl webui` from anywhere:**
  - inside a project, it opens that project;
  - elsewhere, the last one used, or a project list.
  - Running panels are already recorded in `~/.deployctl/panels/<port>.json` (0.13).
- **Top-right switcher:** every project, with its live state (running tag or "not deployed").
  - Choosing one starts that project's panel if it isn't running: a detached process, like
    jobs, through a token-protected `POST`.
  - Then it navigates there.
  - `+ Add project…` at the bottom.
- **Safety:** confirmation dialogs name the **project** as well as the environment, hosts and
  tag. The tab title already does (`deployctl · <project> · <env>`).

## 3. Add a project — new first deployment, or import

`+ Add project…` asks for the **repository path** and checks it:

| Found at that path | Offered |
|---|---|
| `deploy/` with config | add it and open it |
| `deploy/project/` without config (a teammate's clone) | **Import** — the 0.13 dialog: exported file plus passphrase, then all configuration is set |
| no `deploy/` | **New project**: a form for mode (single/cluster), environment name, project basics (name, domain, image repo, hosts) and the app contract (`project.env`: app module, health path, migrate command, Celery app, Dockerfile/build context/targets). It runs `deployctl init` and writes the values, then lands on **Setup** |
| a copied-in `deployctl/` | `deployctl adopt` (plan, then apply) |

- **Joining an existing project needs only three things:** `gh` logged in, access to the
  repository, and their ssh key on the server. The panel checks and explains each.
- **The first deployment stays manual,** from the laptop: Setup → Bootstrap → First deploy
  (Regenerate, Validate, Doctor, Init, SSL, Status). It is **not** through CI/CD. CI/CD is set
  up afterwards on its tab.

## Engineering rules — keep it simple

- **Every panel button runs one deployctl command,** so everything the panel does can be done
  from the CLI.
- **One module per concern:** `cli/access.py`, `cli/projects.py`, and the project-switching
  routes in their own panel module. Don't grow `routes.py` further.
- **The panel stays as it is:** no JavaScript framework, no CDN, no inline script or style (the
  CSP), `data-act` delegation, and the wiring tests stay green.
- **Files deployctl keeps for itself live in `paths.state_home()`:** folders 0700, secret files
  0600, small TOML/JSON.
- **Tests come with each part.** Browser end-to-end checks use scratch projects and unroutable
  test hosts, **never real servers**.
- **Docs, the changelog and the version bump go in the same PR.**
- **Git:** branches created with `--no-track`; **no Claude co-author trailers** in commits or
  PRs.

## Decisions already made — do not reopen

- **Project config stays per project** in `deploy/config/` (gitignored). Personal keys are
  never exported. Export and import exist (0.13).
- **Registry access:** the `gh` login by default, a narrow token optional, CI uses
  `GITHUB_TOKEN`, and hosts are logged out after every pull.
- **One process per project,** plus a switcher.
- **The first deploy is manual,** not through CI.
- **`IMAGE_TAG` in config** stays deprecated until 2.0.

### Settled (what 0.14 built)

- **Which panel starts another:** any panel, and the home panel, through a same-origin,
  token-protected `POST /projects/open` that takes a project **name** only. The server looks
  it up and builds the address. There is no separate launcher: the home panel, on 8765, is
  the project list for when there is no project to open.
- **Ports:** assigned once, from 8766, to the lowest port that is neither assigned nor
  listening, and stored. They change only through `projects add PATH --port P`. A port held
  by anything else is a loud error, never a silent swap.
- **The New form:**
  - shape and environment;
  - project name, domain, subdomain and image (suggested from `origin`, lowercased);
  - servers, SSH user, and certificate email (single only);
  - the app contract, with defaults from `PROJECT_STUB` and a "runs Celery" switch.

  Nothing secret: databases and passwords stay in Configure. It runs `init --set`.
- **`config/local.env`** stays, as a per-project override above the saved token and `gh`.

**Where the build departed from this brief**
- **`~/.deployctl/projects.json`, not `.toml`.** Python has no TOML writer, and a hand-rolled
  one breaks on some characters.
- **`webui` outside a project always opens the home panel,** never the last project used, so
  nobody lands on a production project by accident.
- **The switcher reads each project's running tag live** (`deploy status`, lazily, cached for
  15 seconds), not from a recorded file that goes stale when CI or a teammate deploys.
- **A copied-in deployctl gets the `adopt` commands to run in a terminal,** not plan/apply in
  the panel. It is a one-time migration that rewrites git-tracked files.
- **`panels/<port>.json` records are gone.** A panel is found by asking its port
  (`/healthz`), because the records raced uvicorn's startup, which runs before the port is
  bound.

## Done when

- **Adding projects:** a second project can be added by path and switched to and from, with
  running jobs preserved and both panels safe.
- **Joining:** a teammate's fresh clone goes from Add project, to Import, to *Your access* all
  green, to working, with `gh`, repository access and an ssh key as the only prerequisites.
- **New project:** a brand-new project goes from Add project, to the New form, to Setup, to
  first deploy, to CI/CD, to live, driven from the panel, with the root bootstrap script as the
  only terminal step.
- **Docs:** README, Getting started and First deployment are enough for a new user without
  help.
