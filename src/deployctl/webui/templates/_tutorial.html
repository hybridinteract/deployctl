Start here

deployctl runs on your machine. It renders configuration files, copies them to your servers over SSH, and tells Docker there to pull an image and start. Nothing is installed on the servers except Docker itself, and no agent runs there.

There are two shapes. Pick the one you are building:

Four things worth understanding before you start

1 The servers never build anything
Your image is built once — in CI, or on your machine — and pushed to a registry with an immutable tag. Every server pulls that exact tag. A deploy therefore cannot produce a different result on different machines.
2 Everything is pushed over SSH
deployctl uses your own SSH keys and agent. There is no daemon on the servers to compromise, and anything the tool does you could do by hand with ssh, rsync and docker compose.
3 One host is the primary
Database migrations run there, once{% if tut.with_beat %}, and the scheduler runs there and nowhere else — two schedulers means every scheduled job fires twice{% endif %}. deployctl generates a different compose file for the primary than for the others so this cannot drift.
3 Your data lives on this one machine
Postgres is a Docker volume on the server. That is the only copy. Set up backups in the same session you set up the deploy — step F ends with it.
4 Config is files, and the panel edits them
The Configure tab writes the same config/*.env files the CLI reads. There is no hidden state: whatever you do here, you can do in an editor, and vice-versa.

Part A Get a server

Any provider works — a DigitalOcean droplet, an AWS EC2 instance, a Hetzner or Linode VPS. deployctl only needs SSH access and Docker.

A1 Create the machine
  • Image: Ubuntu 24.04 LTS, or the current LTS.
  • Size: 2 vCPU / 4 GB is comfortable — this machine runs the app, workers, Postgres and Redis together. 2 GB works for a small database with one or two workers. 2 vCPU / 4 GB per host. The databases are managed services, so the hosts only run the app and workers.
  • SSH key: add your public key at creation time. Password login is a dead end — deployctl never types a password.
  • Networking: put every host, the load balancer and both databases in the same region and the same private network / VPC. That is how the hosts reach the databases privately.

Create one machinetwo to start with — adding a third later is the same steps again.

A2 Note the addresses

Most providers give a machine two addresses. You need to keep them apart:

  • Public IP — what you SSH to, and what goes in the Hosts section of the Configure tab.
  • Private IP — used only for the databases' trusted sources list for internal traffic. It does not go into any deployctl setting.
Putting a private IP in Hosts is a common early mistake — the panel then cannot SSH anywhere, and Doctor reports every host unreachable.
A3 SSH in for the first time

Which user you log in as depends on the provider:

# DigitalOcean, Hetzner, Linode, most VPS providers
ssh root@{{ tut.first_host }}

# AWS EC2, Ubuntu image
ssh -i ~/.ssh/your-key.pem ubuntu@{{ tut.first_host }}

# AWS EC2, Amazon Linux image
ssh -i ~/.ssh/your-key.pem ec2-user@{{ tut.first_host }}
EC2 key files: if SSH says UNPROTECTED PRIVATE KEY FILE it is refusing to use a key other people could read. That is the first of several permission problems in this guide, and the fix is always the same shape — tighten the mode: 
chmod 400 ~/.ssh/your-key.pem
Do Part B on every host. Nothing later works until all of them pass step B7.

Part B Bootstrap the server

This is the only time you run commands on the server by hand. After this, deployctl does everything over SSH. Run these as root (on EC2, put sudo in front of each command, or run sudo -i once).

B1 Update the system
apt-get update && apt-get upgrade -y

Takes a minute or two. If it asks about a config file, keep the existing version.

B2 Install Docker
curl -fsSL https://get.docker.com | sh

That installs the engine and the Compose plugin together. Check both:

docker --version
docker compose version

It must be docker compose with a space. The old docker-compose binary is not used and does not need installing.

B3 Create the deploy user

deployctl logs in as an unprivileged user that is allowed to use Docker — not as root. This environment expects it to be called {{ tut.ssh_user }}.

adduser --disabled-password --gecos "" {{ tut.ssh_user }}
usermod -aG docker {{ tut.ssh_user }}

# give it the same SSH key you just logged in with
mkdir -p /home/{{ tut.ssh_user }}/.ssh
cp ~/.ssh/authorized_keys /home/{{ tut.ssh_user }}/.ssh/
chown -R {{ tut.ssh_user }}:{{ tut.ssh_user }} /home/{{ tut.ssh_user }}/.ssh
chmod 700 /home/{{ tut.ssh_user }}/.ssh
chmod 600 /home/{{ tut.ssh_user }}/.ssh/authorized_keys
Those last two chmod lines are not optional. SSH refuses to use a key file that the group or other users can read, and it fails silently — you get "permission denied (publickey)" with nothing in the client output explaining why.
B4 Create the deploy directory

Everything deployctl ships lands here. It must be owned by {{ tut.ssh_user }}, not by root.

mkdir -p {{ tut.remote_dir }}
chown -R {{ tut.ssh_user }}:{{ tut.ssh_user }} {{ tut.remote_dir }}
The single most common permission failure. If this directory — or any directory inside it — ends up owned by root, a deploy fails part way through: rsync copies some files, then stops with "permission denied", and the stack is left half updated. It happens when someone runs a deploy as root once, or creates a subdirectory with sudo. Doctor checks every directory a deploy writes into and prints the exact chown to run.
B5 Add swap

A safety net so a memory spike during an image pull does not get the database killed.

fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
B6 Firewall

Open 22 from your IP, and 80 and 443 from anywhere.

Port 80 must stay open permanently, not just for the first certificate. Let's Encrypt uses it for every renewal; close it and the certificate quietly expires in 90 days.

Open 22 from your IP only, and 80 from the load balancer only. Nothing else needs to be reachable — TLS terminates at the load balancer, so the hosts speak plain HTTP on the private side.

Use your provider's cloud firewall for this, and leave ufw inactive. Running both is the classic way to lock yourself out of a server.

ufw status    # expect: Status: inactive
B7 Verify from your own machine

Leave the server's shell and run this locally. It is exactly what Doctor checks:

ssh {{ tut.ssh_user }}@{{ tut.first_host }} docker ps

You should get a container table — empty is correct at this point. What you must not get:

  • permission denied (publickey) — the key copy in B3 did not work, or the .ssh permissions are wrong.
  • permission denied while trying to connect to the Docker daemon — the user is not in the docker group yet. Re-run the usermod line; group membership only applies to new sessions, so log out and back in.
Repeat B1–B7 on every host before continuing.

Part C Cloud services & DNS

Nothing to provision. In this shape Postgres and Redis run as containers on the server you just set up, and deployctl generates their passwords for you.
C1 Managed Postgres

Create it in the same region and private network as the hosts. From its private connection details, copy the host, port, database, user and password into the Configure tab's database section.

Then add every host to the database's trusted sources / allowed IPs. A host that is missing cannot connect at all, and the deploy fails at the migration step.
C2 Managed Redis

Same region and network. Use the TLS port, and set:

REDIS_SSL=true
REDIS_SSL_CERT_REQS=none   # encrypted, but the provider CA is not public
Add every host to Redis's trusted sources too. This is the failure everyone hits once: people remember Postgres and forget Redis. The API comes up perfectly healthy — it only needs the database — while the workers never connect and no background job ever runs. Nothing in the deploy output says "Redis".
C3 Load balancer
  • Forwarding: start with HTTP :80 → HTTP :80; add HTTPS :443 → HTTP :80 once you have a certificate.
  • Health check: HTTP, port 80, path /health.
  • Sticky sessions: off — the app is stateless.
  • Proxy protocol: off — nginx here is not configured for it, and turning it on breaks every request.
  • Add all hosts as backends. Note the load balancer's public IP for DNS.

The health check hits hosts by IP. nginx pins a trusted Host header for exactly this reason, so the check gets a 200 rather than a 400 — you do not have to configure anything for it.

C{% if tut.cluster %}4{% else %}1{% endif %} DNS

Point your domain at {% if tut.cluster %}the load balancer's IP{% else %}the server{% endif %}:

A    {{ tut.domain }}    →    {% if tut.cluster %}<load-balancer-ip>{% else %}{{ tut.first_host }}{% endif %}

Do this now — propagation can take up to an hour, and you can carry on with the rest while it settles.{% if tut.tls_le %} Certificate issuance in Part F will not work until this resolves.{% endif %}

Part D Configure

Everything from here happens in this panel. Open the Configure tab and work down the sections; each field has help text under it. These are the ones that matter most:

D1 Project and servers
  • Project name — lowercase; it prefixes container, network and volume names.
  • Base domain and API subdomain — together they make {{ tut.domain }}.
  • Hosts — the public IPs from step A2.{% if tut.cluster %} Mark one as primary: it runs the migrations{% if tut.with_beat %} and the scheduler{% endif %}.{% endif %}
  • SSH user — {{ tut.ssh_user }}, the user created in B3.
  • Remote directory — {{ tut.remote_dir }}, the directory created in B4. These two must match what is actually on the server.
D2 Registry

Two settings that are easy to mix up because they sit next to each other:

  • Image repository — where the image lives, e.g. {{ tut.image_repo }}.
  • Registry user — who logs in, e.g. {{ tut.registry_user }}. A plain account name, never a URL.
  • Registry token — for GitHub, a classic personal access token with only read:packages. If your organisation uses SSO, authorise the token for the org afterwards or the pull returns 401.

Validate catches a repository pasted into the user field — but only after you save, so it is worth reading them back once.

D3 Save

Click Save at the bottom of the Configure tab. It writes the same config/*.env files the CLI reads. Secrets you leave blank keep whatever is already stored, so re-saving never wipes a password you cannot see.

Then check what the tool actually resolved, with secrets masked: Preview resolved config, next to Save.

Part E Publish an image

The servers pull; they never build. So there has to be an image in the registry before the first deploy. Two ways:

E1 From CI — recommended
deployctl ci init --branch main

That writes .github/workflows/build-image.yml, which builds and pushes {{ tut.image_repo }}:<short-sha> on every push to that branch. Then, once, in the GitHub repository:

Settings → Actions → General → Workflow permissions → "Read and write permissions" → Save.

Skip that and the build goes green until the push step, which fails with denied: permission_denied (403). It is the most common CI setup mistake.

Commit, push, and wait for the run to go green. The run summary prints the tag.

E2 Or from your own machine
deployctl image push

Builds, tags with the current git short SHA, pushes, and writes that tag into the config for you. Needs Docker locally.

E3 Pin the tag

In Configure → Image, click ↓ fetch tags from the registry and click the newest one, then Save.

Use a real tag, not latest. A moving tag means two hosts can pull two different builds from the same deploy, and rollback has nothing to roll back to.

Part F First deploy

Run these in order. Each one catches what the next assumes, and the output streams into the pane on the right.

F1 Regenerate

Renders every configuration file from your settings. Passwords are minted once and reused, so this is safe to run any time — it never logs users out.

{{ run('regenerate', 'Regenerate') }}
F2 Validate

Reads the rendered files back and checks them against the configuration — including file permissions{% if tut.with_redis %}, the Redis password file among them{% endif %}.

Exit 0 is clean, 2 is warnings only, 1 means errors you should fix before deploying.

{{ run('validate', 'Validate') }}
F3 Doctor

Connects to every host and checks the things that make a deploy fail half-way: SSH, Docker without sudo, the CPU architecture, whether the image can be pulled from there, and whether the permissions are workable — both on the files here and on the directories a deploy writes into over there.

{{ run('doctor', 'Doctor') }}
If it reports a permission problem, most of them can be repaired for you. From a terminal (Terminals tab → Local): 
deployctl deploy doctor --env {{ env }} --fix
--fix only changes file modes — locally, and on hosts where {{ tut.ssh_user }} already owns the file. Anything needing root is printed as an exact sudo chown for you to run, rather than the deploy user being given a way to escalate.
F4 Init

The real one. It copies the artifacts to {% if tut.cluster %}every host{% else %}the server{% endif %}, logs Docker in to the registry, pulls the image{% if tut.has_migrate %}, runs the database migrations once on the primary{% endif %}, starts everything{% if tut.cluster %} — primary first, then the rest{% endif %}, and waits for the health check to pass.

{{ run('init', 'Init', true) }}
{% if tut.tls_le %}Init also creates a temporary 1-day self-signed certificate, because nginx cannot start without a certificate file at all — and without nginx on port 80 there is no way to answer the Let's Encrypt challenge. Step F5 replaces it.{% endif %}

Rehearse against the staging CA first — it has no rate limit and proves DNS, ports and the challenge path all work. From a terminal:

{{ run('ssl-setup', 'SSL: obtain', true) }} {{ run('ssl-check', 'SSL: check') }}

  2. Add its private IP to both databases' trusted sources.
  3. Attach it to the load balancer.

When it breaks

The failures that actually happen, and what each one really means. Permission problems come first because they are the ones that never look like permission problems.

Permissions

{% if tut.with_redis %}
Deploy fails with dependency failed to start on api, worker{% if tut.with_beat %} and beat{% endif %} — but nothing is wrong with any of them
What is really happening: the Redis container exited. Its password lives in a file that is mounted in from the host, and Redis runs as uid 999 inside the container — an identity that owns nothing on the host. If that file is 0600 and owned by {{ tut.ssh_user }}, Redis cannot read its own config and quits. Compose then reports the failure on every service that depends on Redis, and never on Redis itself.
Fix: Regenerate — the renderer sets the mode correctly and rsync carries it to the host. Validate and Doctor both check for it explicitly, and deployctl deploy doctor --env {{ env }} --fix repairs it in place. The file is meant to be world-readable: it is protected by {{ tut.remote_dir }}'s ownership, not by its own mode.
{% endif %}
rsync: permission denied mid-deploy, some files already copied
Cause: a directory under {{ tut.remote_dir }} is owned by root — from a deploy run as root once, or a sudo mkdir.
Fix: Doctor names the exact directory. On the host: sudo chown -R {{ tut.ssh_user }}: {{ tut.remote_dir }}. --fix deliberately will not do this one — repairing it needs root, and a deploy user that can become root defeats the point of having one.
permission denied (publickey) when SSHing as {{ tut.ssh_user }}
Cause: the key was never copied (step B3), or .ssh is too permissive. SSH silently ignores a key file others can read.
Fix: on the host, as root — chmod 700 /home/{{ tut.ssh_user }}/.ssh && chmod 600 /home/{{ tut.ssh_user }}/.ssh/authorized_keys.
UNPROTECTED PRIVATE KEY FILE on your own machine (EC2)
Cause: the downloaded .pem is readable by other local users.
Fix: chmod 400 ~/.ssh/your-key.pem.
permission denied while trying to connect to the Docker daemon
Cause: {{ tut.ssh_user }} is not in the docker group — or was added while already logged in.
Fix: usermod -aG docker {{ tut.ssh_user }}, then log out and back in. Group membership only applies to new sessions, which is why this looks like the command did nothing.
/docs returns 403 even with the right password
Cause: the htpasswd file cannot be read by nginx's worker uid, or is empty. deployctl creates it empty on purpose — the docs fail closed until you put a user in it.
Fix: generate a line with htpasswd -nbB user 'password', write it to {{ tut.remote_dir }}/nginx/auth/.htpasswd on the host, make sure it is readable (chmod 644), and reload nginx.

Everything else

{% if tut.tls_le %}
Certificate request fails with Connection refused against an IP you do not recognise
Cause: the domain has more than one A record. Let's Encrypt resolves the name itself and validates against whichever address it gets — so a leftover record pointing at an old server fails the challenge, even though {{ tut.domain }} reaches the right host in a browser. Read the IP in certbot's error: if it is not {{ tut.first_host }}, this is what happened.
Fix: check every record, not just the first — dig +short {{ tut.domain }} should print exactly one line. Remove the stale ones at your DNS provider, wait out the TTL, then rehearse with deployctl ssl setup --env {{ env }} --staging before spending a real issuance. ssl setup now refuses to run when an extra record cannot answer on port 80.
{% endif %}
Health check times out — status 400
Cause: the app is rejecting the Host header nginx sends. It reached the app, so networking is fine.
Fix: Regenerate and Update to ship the current nginx config, and check the trusted hosts list includes {{ tut.domain }}.
Health check times out — status 502 or 503
Cause: nginx is up but cannot reach the app. Usually the app crashed on boot, or it cannot reach the database.
Fix: Logs tab → the failing host, and read the app container's first 50 lines.
Health check times out — status 000
Cause: nothing is answering on port 80 — nginx did not start. A bad extra nginx config will do this{% if tut.tls_le %}, as will a missing certificate file{% endif %}.
Fix: Logs tab, look at nginx. Run Validate first — it parses the generated config before it can reach a server.
docker compose pull → denied or not found
Cause: the tag does not exist yet, the package is private and the registry token is missing or expired, or the token has not been SSO-authorised for the organisation.
Fix: confirm the CI run is green, re-fetch tags in Configure, and re-check the registry user/token pair from step D2.
exec format error when a container starts
Cause: the image was built for a different CPU — classically an arm64 image built on an Apple Silicon Mac, deployed to an x86 server.
Fix: set IMAGE_PLATFORM=linux/amd64 and rebuild. Doctor compares the host's architecture to the configured platform and catches this before anything is torn down.
Workers are running but no background job ever executes
Cause: almost always Redis. Is every host in the Redis trusted sources, not just Postgres?
Fix: add them. Also confirm anything that waits for Redis in your entrypoint speaks TLS — a plain redis-cli ping never returns against a TLS-only managed Redis, so the container waits forever.
{% if tut.with_beat %}
Scheduled jobs fire twice
Cause: two schedulers are running. Validate catches this in the generated files; at runtime it means a stale container is still up on a host that is no longer the primary.
Fix: Terminals tab → SSH to the host → docker ps, and stop the leftover.
{% endif %}
